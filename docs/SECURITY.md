# Seguridad y privacidad — MVP

- Better Auth es la solución para email/contraseña y sesiones. El core está integrado con Better Auth/adaptador Prisma 1.7.11, Fastify 5.12.7 y Prisma 7.10.1; la migración y los flujos se probaron contra PostgreSQL 17 efímero aislado. Repetir la validación en CI y tras cualquier actualización de versiones. No implementar credenciales, sesiones ni criptografía artesanal como sustituto.
- El registro público de Better Auth permanece deshabilitado. Solo administradores autenticados crean/listan/revocan invitaciones; la aceptación requiere estado `ACTIVE`, token válido y email normalizado asociado. El adaptador SMTP genérico usa Mailpit solo en desarrollo; `ACTIVE` requiere que SMTP acepte al destinatario, sin garantizar la recepción final.
- Vincular cada invitación a un email normalizado. Generar un token aleatorio de alta entropía y almacenar únicamente su hash; expira a los 7 días y se acepta una sola vez. La aceptación debe ser atómica y resistir solicitudes concurrentes. No exigir verificación adicional del correo después de aceptar correctamente la invitación.
- Los roles globales son el enum de base de datos `admin` y `user`; solo el servidor puede asignarlos. Rechazar cualquier intento de asignación o elevación desde parámetros enviados por el navegador. El bootstrap del primer admin es un comando local con confirmación, no un endpoint HTTP. La propiedad de listas compartidas es independiente del rol global.
- Crear el primer administrador solo mediante un procedimiento local controlado, nunca mediante endpoint público.
- Configurar sesiones seguras y cookies con atributos HttpOnly, Secure y SameSite según el entorno. Mantener CSRF y comprobaciones de origen habilitados; no desactivar estas protecciones.
- Aplicar rate limiting a autenticación, recuperación e invitaciones; evitar respuestas que faciliten enumeración de usuarios.
- Mailpit con Docker se usa exclusivamente para desarrollo local: la interfaz web y SMTP se publican en loopback, no requiere credenciales reales, no debe exponerse públicamente ni emplearse como proveedor real, y sus mensajes son efímeros. Las pruebas automatizadas deben usar un remitente simulado y nunca enviar correos reales. No se ha aprobado un proveedor remoto.
- La solicitud de recuperación usa respuestas genéricas, rate limiting y tokens Better Auth de una hora y un solo uso. Los tokens viajan en el fragmento del enlace, no en la petición de navegación HTTP; el frontend (WEB-AUTH-001) los lee del fragmento, los retira de la barra de direcciones antes de montar la interfaz, no los guarda en `localStorage` ni `sessionStorage` y los envía solo en el cuerpo de la petición a la API. Las invitaciones creadas por CLI local pueden llevar solo el token; el formulario pide el correo y el servidor valida ambos datos sin confiar en roles enviados por el cliente. El cambio de contraseña invalida sesiones existentes. Si el envío SMTP falla, se elimina el token temporal cuando la base de datos permite la limpieza; la respuesta pública sigue siendo genérica.
- No se registran ni se devuelven por HTTP tokens de invitación o recuperación. Los comandos CLI administrativos solo admiten el PostgreSQL del Docker Compose local y pueden mostrar un token de invitación solo para pruebas. Exigen `NODE_ENV=development`, destino exacto en `LOCAL_AUTH_ALLOWED_DATABASES`, Docker local no remoto, el único contenedor activo etiquetado con el proyecto/servicio esperados y una comprobación SQL de base/usuario/esquema/IP/puerto observados por la conexión efectiva de Prisma frente a la IP interna y puerto publicado del contenedor. Revalidan el mismo contenedor tras la confirmación aleatoria vinculada a operación/destino/contenedor e inmediatamente antes de escribir. Cualquier error o discrepancia bloquea la operación. No son mecanismos de bootstrap para staging o producción.
- La comprobación presupone que el daemon Docker y la configuración local del proyecto son de confianza. Una persona con control del daemon puede crear contenedores y etiquetas deliberadamente engañosos o cambiar la configuración; una restauración de datos dentro del mismo contenedor autorizado permanece dentro del destino permitido por la política MVP. Esto no sustituye controles operativos del host ni un procedimiento separado de producción.
- Las invitaciones se crean como `PENDING_DELIVERY` y no pueden aceptarse hasta que SMTP acepte al destinatario y la transición a `ACTIVE` se confirme en PostgreSQL. Ante fallo SMTP pasan a `DELIVERY_FAILED` si la DB está disponible; si no, permanecen `PENDING_DELIVERY`, también inutilizable. Si SMTP acepta el mensaje pero PostgreSQL falla antes de confirmar la activación, la API devuelve un error controlado y la invitación permanece no utilizable, salvo que la transacción ya se hubiera confirmado aunque se perdiera su respuesta. No hay reintentos automáticos. Una vez recuperada la DB, el administrador consulta el estado: conserva el envío solo si figura `ACTIVE`; si figura `PENDING_DELIVERY` o `DELIVERY_FAILED`, revoca la invitación y emite otra nueva. El token anterior nunca se reactiva ni reutiliza.
- Validar entradas y aplicar autorización en servidor para cada operación sobre biblioteca, valoraciones, progreso y listas.
- Las valoraciones solo se crean para títulos en la biblioteca personal. Un usuario no puede leer ni modificar los datos personales de otro.
- Invitaciones de un solo uso con token aleatorio almacenado como hash y fecha de vencimiento.
- Secretos en variables de entorno del servidor o gestor de secretos; `.env` real fuera del control de versiones. No introducir credenciales reales en archivos versionados.
- Controlar dependencias, ejecutar CI, limitar CORS y generar logs sanitizados. No registrar contraseñas, cookies, tokens de sesión/invitación ni datos personales innecesarios.

- Preparar política de borrado y exportación de datos; revisar RGPD si hay usuarios reales.
- **TMDB (ADR-007, diseño aprobado; cliente implementado localmente en TMDB-API-001, pendiente de PR y CI; búsqueda y detalle implementados localmente, pendientes de revisión de la rama):** `TMDB_READ_ACCESS_TOKEN` es un secreto exclusivo del backend: nunca en el navegador, respuestas, logs, errores, repositorio ni CI. El cliente usa host fijo `api.themoviedb.org` (sin URL base configurable ni URLs de usuario) para evitar SSRF; las rutas se construyen en servidor con enteros validados. Entradas validadas explícitamente en los módulos de catálogo (propiedades desconocidas rechazadas, `q` de 1–100 caracteres, página 1–500, `tmdbId` entero positivo) y rate limiting propio. Timeouts y reintentos acotados solo en GET idempotentes (implementados en el cliente: plazo por intento garantizado incluso si el transporte ignora la cancelación, presupuesto total, máximo 2 reintentos, cuerpo limitado a 2 MB leído incrementalmente y redirecciones rechazadas, `Authorization: Bearer`); un 429 de TMDB se traduce a 429 (con `Retry-After` solo si es un entero de 0 a 3600). Los logs solo registran tipo de error, motivo, estado, intento y duración, sin credenciales, consulta ni fragmentos de cuerpo. Si TMDB no está disponible se devuelve un error controlado (502/503/504); un 401/403 de TMDB o un token ausente se presentan como 503 sin revelar la causa; no se sirven datos caducados y los datos propios no se ven afectados. Las imágenes se cargan desde la CDN oficial `image.tmdb.org` con URLs construidas en servidor y tamaños permitidos (sin proxy). Las pruebas y CI usan mocks y fixtures, sin token real. El contenido de TMDB no se usa en entrenamiento ni IA generativa.

## Pruebas de seguridad que bloquean entrega

Usuario A no puede leer/modificar la biblioteca, valoraciones o progreso de B; ver listas privadas sin pertenencia; editar una lista tras ser eliminado; ni cambiar roles sin permiso. El registro sin invitación, la emisión de invitaciones por usuarios no administradores y la elevación de rol desde el cliente deben rechazarse. Invitaciones vencidas o ya consumidas, incluidas aceptaciones concurrentes, no deben crear más de una cuenta. Los miembros pueden añadir y retirar títulos, pero no administrar miembros ni eliminar la lista. Contraseñas, cookies, sesiones e invitaciones no deben aparecer en logs ni respuestas API. Solicitudes de origen no confiable no deben omitir las protecciones CSRF. Cuando se implemente el catálogo: las rutas de catálogo sin sesión devuelven 401, y el token TMDB no debe aparecer en respuestas, logs ni bundle del frontend.


### Detalles enriquecidos — implementación local TMDB-API-003

Solo mocks hasta resolver TMDB-TERMS-001. La identidad principal de respuesta y cualquier
ID presente en anexos deben coincidir con el título solicitado; en caso contrario 502,
sin caché. Reparto, equipo y proveedores requieren IDs enteros seguros positivos y nombre.
Las URLs de fotos/logos se construyen con rutas de imagen permitidas en la CDN oficial;
vídeos solo YouTube/Vimeo con claves validadas y URLs construidas en servidor, sin autoplay.
Enlaces de streaming solo HTTPS al título y región ES en TMDB, sin credenciales ni
parámetros adicionales. Campos desconocidos y precios se descartan. La caché de metadatos
no concede acceso: Better Auth se verifica en cada petición. El futuro modal solo podrá
cargar terceros tras acción del usuario; la API no contacta con YouTube, Vimeo ni JustWatch.
La atribución JustWatch y las condiciones de proveedores siguen sujetas a verificación
antes de activar datos reales; esta implementación no aprueba su uso legal.
